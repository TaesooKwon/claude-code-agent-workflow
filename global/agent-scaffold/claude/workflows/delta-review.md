# 델타형 단일 에이전트 리뷰 — 프롬프트 템플릿 (2026-09-03)

> 레포 규약이 빌트인 `Skill(code-review)` 를 대체 엔진으로 골랐다면 소형 A = 빌트인 `low`(`mark-review.sh --begin` → 리뷰 → `--builtin <결과 JSON 파일>`)이고, 이 템플릿은 빌트인을 쓸 수 없을 때 쓴다.
> 빌트인 Result 가 `(none)` 이면 `[]` 로 옮겨 `--builtin` 에 넘긴다. 그 밖의 배열 아닌 텍스트 = 리뷰 실패 → 이 템플릿(또는 `commit-review.js`)으로 리뷰.

> 용도 두 가지: ①**소형 A 리뷰**(≤5파일·인증/인가·상태전이·비동기 배선·신규 스키마 무변경·단위테스트 커버 — 셋 다일 때 `commit-review.js` 대신)
> ②**델타 재리뷰**(1차 리뷰 CONFIRMED 를 수리한 뒤). 워크플로의 finder/verify 에이전트는 주소가 없어 `SendMessage` 로 이어 붙일 수 없다 —
> 그래서 **새 단일 에이전트에 1차 지적·수리 주장을 전사**해서 준다. 실행 = `Agent`(세션 모델, 백그라운드, `name:` 금지). 결과는 아래 스키마로 받아
> **CONFIRMED 제목·파일·라인 1:1 수리 체크리스트**로 옮겨 적는다(빠뜨림 방지).

## 프롬프트 골격(빈칸을 채워 그대로 전달)

```
너는 커밋 전 코드 리뷰어다. 스코프 = 아래 diff 만(diff 밖 기존 성질·공통자산 지적 금지 — 지적마다 "걸리는 변경 라인"을 반드시 적는다).
레포: <REPO_ROOT>   대상 diff: `git diff --cached` (또는 첨부)   의도: <INTENT 한 문단>
확정 사실(반박 금지, 그러나 첫 항목으로 "이 전제가 틀렸다면"을 1줄 검토): <FACTS 불릿>

[모드 = 소형 A]           관점 = behavior(의도대로 동작하나·경계값·오류경로) + regression(기존 호출자·계약·상태전이가 깨지나).
[모드 = 델타 재리뷰]      1차 지적과 수리 주장을 아래에 전사한다. 판정할 것: ⓐ수리가 절반인가(지적의 모든 경로를 막았나) ⓑ수리가 새 결함을 만들었나
                          ⓒ수리가 지적과 무관한 곳을 건드렸나. **이미 기각된 지적은 다시 올리지 마라**(목록 첨부).
                          ⓓ**수리로 새로 쓴 주석·문장 자체가 참인가** — 정정문이 또 거짓인 사고가 이 레포에서 반복됐다
                          (2026-09-07 한 커밋에서 1차 3건 → 수리 후 1건 → 그 수리 후 2건). 문장 속 명사를 그 파일에서
                          grep 하고, 같은 diff 의 테스트가 그 문장을 반증하지 않는지 대조하라. [[comment-asserts-facts-outside-the-code]]
  1차 지적: <제목 | 파일:라인 | 요지> …
  수리 주장: <무엇을 어떻게> + 수리 diff: <첨부>
  기각 목록(재상정 금지): <제목 …>

하한선 5항목을 체크리스트로 훑어라(해당 없으면 N/A 로 명시): ①트러스트 경계 입력검증 ②데이터손실 방지 에러처리(경합 포함) ③보안(인가·시크릿·운영가드) ④접근성 ⑤명시요청 기능.
스택 함정(레포 규약): <예: Java 8 한정 · MyBatis CDATA · 매퍼 SELECT * 금지 · 소프트 딜리트 · 비동기 재진입/last-wins · App 다이얼로그 싱글턴 …>

반환(JSON 만):
{ "reviewedFiles": [...], "findings": [ { "severity": "BLOCK|HIGH|MED|LOW", "title": "", "file": "", "line": 0,
    "changedLine": "그 지적이 걸리는 변경 라인 원문", "why": "구체 입력/상태 → 잘못된 결과", "fix": "" } ],
  "premiseChallenge": "확정 사실 중 의심되는 것(없으면 null)", "notes": "" }
```

## 회수 절차
1. `findings` 를 severity 순으로 **체크리스트**(`- [ ] <title> — <file>:<line>`)로 옮겨 적는다. 지적 0건이면 "0건"이 아니라 `reviewedFiles` 가 스테이징 파일 전부인지 먼저 대조한다(미수행과 0건 구분).
2. **수리 전 모집단 표를 먼저 적는다(필수).** 지적 1건을 고치기 전에, 그 수리가 건드리는 **필드·분기·호출경로를 전수**로 표에 적고(모집단 경계 = 트리·확장자·소유 축을 세기 전에 명시) 같은 형태를 `grep` 으로 전부 찾아 **한 라운드에 함께** 고친다. 짚어준 자리만 고치면 다음 라운드에 그대로 재출현한다(2026-09-08 실측 3라운드 15→11→8). 표 없이 시작한 수리는 발산의 주된 생성기였다. [[review-loop-divergence-stop]]

   | 지적 | 모집단(전수 목록) | 이번 라운드에 고칠 것 | 남기는 것·사유 |
   |---|---|---|---|

3. BLOCK/HIGH 는 수리 → `git add` → 이 템플릿의 **델타 재리뷰 모드**로 1회 더. MED/LOW 는 수리하거나 사유를 적고 남긴다.
   **주석 지적의 수리는 단언을 지우는 방향이 기본**이다 — 역할·불변식만 남기고 새 사실(전칭·범위·다른 파일 동작)을 들이지 않는다. 수리를 `git add` 하기 전에 `bash .claude/scripts/comment-selfcheck.sh --repair` 로 새로 쓴 문장(ⓓ)을 본다. [[comment-asserts-facts-outside-the-code]]
   ⚠️**라운드 상한 2가지** — ⓐCONFIRMED 가 직전 라운드보다 **줄지 않으면** 그 자리에서 멈춘다 ⓑ**줄고 있더라도 3라운드를 넘기면 멈춘다**(단조 감소만으론 종료가 보장되지 않는다). 멈출 땐 라운드별 건수·내 수리가 만든 비율·선택지(범위 축소/설계 재시작/현 상태 커밋)를 사용자에게 보고한다. [[review-loop-divergence-stop]]
4. **중간 라운드 테스트는 영향 모듈만**(`mvn test -pl <모듈> -am -Dmaven.repo.local=…`), **전량 총계는 마커 직전 1회**. E2E 위임은 변경 화면 + 직접 파급 1~2개까지(전체 회귀는 온디맨드).
5. 빌드·단위테스트 총계 확인 → 마커 — **별도 Bash 호출** → 커밋. 워크플로 결과면 `mark-review.sh --result <리뷰 결과 JSON>`, 빌트인(대체 엔진)으로 리뷰했으면 `--builtin <결과 JSON 파일>`(리뷰 직전 `--begin`), 델타형이라 결과 JSON 이 없으면 `--skip-reason "<사유>"`(인자 없는 호출은 마커가 안 찍힌다).
6. 경량 실행(소형 A)했음을 사용자 보고에 적는다(침묵 강등 금지).
