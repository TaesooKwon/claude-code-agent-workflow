# 다층 관통 기능은 얇은 실물 왕복 1회부터 (워킹 스켈레톤)

**조항(전역 §비동기·검증)**: 입력에서 최종 소비(브라우저 렌더)까지 서로 다른 프로세스·파일이 3개 이상 끼면, 층마다 코드를 읽어 "되겠지"로 넘기지 말고 가장 얇은 경로 하나를 끝까지 실행해 통과시킨 뒤 살을 붙인다.

## 경위 (2026-09-07 예시 레포, 게시판 에디터 본문 이미지 첨부)

기능 하나가 **7개 층**을 지난다: 브라우저 JS(`app.js` 이미지 모달) → 서블릿 필터(`HTMLTagFilter`) → 컨트롤러 → HTML 정제(`AppHtmlSanitizer`) → DB → 템플릿(`th:utext`) → 정적 서빙(`/upload/**` 리소스 핸들러).

각 층을 **코드 읽기로만** 판단하고 이어 붙였다. 결과 — 결함이 층마다 **순차적으로** 드러났다.

| 순서 | 발견 시점 | 결함 | 층 |
|---|---|---|---|
| 1 | 리뷰 | 응답 URL 에 컨텍스트패스(`/cms`·`/front`)가 없어 `<img src>` 가 전 화면 404 | 정적 서빙 |
| 2 | 리뷰 | `Jsoup.clean` 이 상대 `src` 를 통째로 제거(`<img alt="x">` 만 남음) → "팝업·설문 수리했다"가 거짓 | 정제 |
| 3 | E2E | FO `HTMLTagFilter` 허용목록이 **Admin 스킴을 복사**해 FO 라우트와 매치 0건 → FO 글쓰기가 최초 커밋 이래 전부 이스케이프 | 필터 |
| 4 | 델타 2R | 2번 수리(`preserveRelativeLinks`)가 스킴 상대 URL 공격면을 신설 | 정제 |
| 5 | 델타 3R | 4번 수리(블랙리스트)에 6종 우회 | 정제 |

**리뷰 CONFIRMED 추이 8 → 5 → 5**(감소 없음), 3라운드 5건은 **전부 내 직전 수리가 파생**시킨 것 = 발산 판정.

## 왜 못 잡았나 — 검증이 못 보는 층

- **목 테스트**: 컨트롤러가 서비스를 부르는 것만 본다. 그 응답이 브라우저에서 로드되는지 모른다.
- **컴파일·lint**: 문자열 URL 의 유효성을 모른다.
- **jsharness**: JS 로직만 본다. 서버 응답 계약·정적 서빙과 무관.
- **단위테스트**: 내가 짠 기대값(`/upload/...`)이 **이미 틀린 전제**였으므로 초록불이 결함을 승인했다.

즉 **층 사이의 접합부**는 어떤 정적 검증도 원리적으로 못 본다. 실행만이 본다.

## 한 번에 되게 하는 법

착수 직후 **가장 얇은 왕복 1회**: BO 에서 이미지 1장 올려 저장 → FO 상세에서 그 이미지가 200 으로 뜨는지. 이걸 먼저 통과시켰다면 결함 1·2·3 이 **동시에** 드러나 설계를 한 번에 잡았다. 비용 20분 대 실제 소모(리뷰 3라운드 + E2E 2회 + 수리 연쇄).

## 발동 판정

- 입력→소비 사이에 **서로 다른 프로세스**(BO 앱·FO 앱·브라우저)가 끼는가
- 또는 **서로 다른 파일 3개 이상**(JS·필터·컨트롤러·템플릿·설정)이 하나의 값을 이어 받는가
- 저장값을 **다른 앱이 렌더**하는가(컨텍스트·도메인·권한 축이 갈린다)

하나라도 해당하면 코드 착수 전 왕복 1회.
