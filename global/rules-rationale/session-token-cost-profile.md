2026-07-31 트랜스크립트 233개(606MB) 실측. 툴 결과 페이로드 **총 ≈3.81M tok**.

| 툴 | 비중 | 콜 | 콜당 평균 |
|---|---:|---:|---:|
| Read | 46.8% | 1,652 | 1,079 |
| Bash | 38.3% | 5,028 | 290 |
| DB MCP | 4.7% | 632 | 283 |
| Edit | 3.8% | 2,951 | 49 |

- **단건 25k tok 초과 텍스트 결과 = 0건** → 낭비는 컨텍스트 폭탄이 아니라 **중간 크기 반복 읽기의 누적**이다. 상위 20파일이 전체 Read 의 43%.
- **콜당 단가 최악 = `.output`·`.txt`(빌드/테스트 로그) 평균 4,900~5,900 tok** — 22콜뿐이라 총량은 작지만 1콜 낭비폭이 가장 크다.
- 반복 상위: `agent_history.md` 115회(81k) · `InspServiceImpl.java` 54회(123k) · `InspController.java` 51회(98k) · `MEMORY.md` 53회.

**Why:** Headroom 같은 서드파티 압축 프록시 도입 판단의 근거 데이터였다([[third-party-tool-adoption-check]]). 결론은 "우리 낭비는 압축으로 줄일 폭탄형이 아니라 습관형" — 프록시보다 읽기 습관 교정이 먼저다.

**How to apply:**
- 빌드·테스트 로그는 파일 통째 `Read` 금지 → `grep -E "ERROR|FAIL|BUILD"` · `tail -n` 경유(콜당 5.9k → 수백).
- 큰 소스·의례 파일 재방문은 `offset`/`limit` 부분 읽기.
- ⚠️**집계를 다시 돌릴 땐 이미지 블록을 반드시 분리**한다. base64 문자수/4 로 세면 스크린샷 1장이 112k tok 로 잡혀 총계가 1.6배 부풀고(6.0M vs 실제 3.81M) 결론이 뒤집힌다. 이미지 토큰 ≈ (w×h)/750.
- 집계 스크립트 원리: `tool_use.id` → `tool_result` 를 이어 툴별 페이로드 합산. Bash 는 `cd X &&` 접두를 벗겨야 실제 명령으로 귀속된다.

## 상시 로드 컨텍스트 예산 (2026-08-10 실측·게이트 신설)

**툴 호출 비용과 별개로, 세션 시작 시점에 이미 나가는 고정비가 있다.** 실측: 전역 `CLAUDE.md` 25.3KB + 프로젝트 `CLAUDE.md` **47.3KB** + `MEMORY.md` 19.5KB = **92KB ≈ 35~45k 토큰**(200k 컨텍스트의 20%). 한 줄 고치는 작업에도 이 비용이 붙는다.

**분리 메커니즘 자체는 정상이다** — memory 본문 668KB/124파일은 회상식, 스킬은 호출식이라 안 붙는다. 문제는 **"상시" 층만 자란다**는 것. 규약에 "간결히" 취지가 있었는데도 프로젝트 규약이 47KB가 됐고, 인덱스는 "한 줄 훅까지만" 규약을 **124줄 중 119줄(96%) 위반**했다 ⇒ 선언으로 안 지켜져 게이트로 승격(`rules-size-check.sh`, 전역 Stop 훅, 하루 1회).

**구조적 한계**: `CLAUDE.md` 는 "필요할 때만 로드"가 **불가능**하다(런타임이 전역+프로젝트 둘만 자동 로드, 중간 레이어를 새로 만들어도 안 읽힌다) ⇒ 유일한 수단은 **"규칙은 남기고 근거는 memory 로 밀어내기"**. 새 층을 만드는 건 답이 아니다.

**섹션별 실측(프로젝트 47.3KB)**: 🎨UI/퍼블 12.8KB(27%) · 🧪검증 9.6KB(20%) · ♻️학습루프 8.0KB(17%) — 상위 3개가 **64%**. 전역↔프로젝트 **원리 중복**도 실측됐다(재진입/in-flight·라이브 리전이 양쪽에 존재) → 배치 3규칙대로 프로젝트엔 레포 고유 계약만 남기면 된다.

**축소 절차(위험 순) — 2026-08-10 A·B·C 전량 수행 완료, 아래는 그 실측**:
1. **인덱스 압축**(위험 0) — 훅만 줄이고 링크는 전량 보존. ✅19.5KB→12.0KB(36%↓), **링크 차집합 양방향 0으로 무손실 실증**. 예시 레포 도 15.4→9.1KB(41%↓).
2. **프로젝트 규약 서사 이관**(위험 중) — 규칙 문장은 남기고 경위·실측만 memory 로. ✅형제레포1 47.3→30.7KB(**35%↓**), 예시 레포 40.9→30.3KB(26%↓). 추정 7~9k 토큰은 대체로 맞았다.
3. **전역 규약**(위험 높음) — ✅26.3→25.5→**25.2KB**(2차 절개로 여유 400B 확보). "최소 절개" = 사례·수치만 빼고 **규칙 문장은 한 줄도 제거하지 않았다**(조항 수 12개 전후 동일로 실증). 서사가 규칙 준수를 떠받치므로 이 선을 넘지 마라.

**최종 상태(2026-08-10 3차)**: 전역 **24,361**(여유 1,239B) · 형제레포1 **30,206**(514B) · 인덱스 **11,904**(384B) = 합계 **64.9KB**(다이어트 전 92KB 대비 **29%↓**). 되돌림 기준선 = `~/.claude/backups/rules-20260810/{pre-trim,baseline}/` — **`CLAUDE.md` 는 git 격리라 이 사본이 유일한 되돌림 수단**이니 다음 축소 전 반드시 갱신한다.

⚠️**전역 규약의 `[[포인터]]` 를 프로젝트 memory 로 밀면 안 된다 — 그 레포에서만 회상되고 나머지는 전부 죽은 링크가 된다.** 실측(2026-08-10 교차검사): 전역 포인터 5개가 형제레포1 외 **6개 레포 전부에서 미존재**였고, `verify-state-claims-before-asserting` 은 두 레포 사본이 이미 **드리프트**해 있었다(2,209 vs 2,501B — 복제안이 실패함을 실증). ⇒ **해법 = 전역 스코프 근거 저장소 `~/.claude/rules-rationale/`**(이 파일이 그 안에 있다). 프로젝트 memory·인덱스에서는 제거했고(양 레포 합계 약 700B 회수) **7개 레포 전건 포인터 해소**를 재검사로 확인했다.

**이 구조가 예산에 주는 효과**: `rules-rationale` 는 상시 로드가 아니므로 크기 게이트 대상이 아니다 — 전역 조항의 서사를 여기로 밀면 **규칙을 하나도 잃지 않고** 예산이 생긴다. 3차 절개에서 [[sample-size-and-premise-errors]] 로 밀어낸 6건 실측 서사가 그 예(전역 −1.2KB).

**축소 실행 시 지킬 것(위 3회 수행에서 굳은 것)**:
- **이관처 memory 실재를 먼저 `grep`** 하고, 없으면 **잘라내기 전에 memory 를 먼저 쓴다**(형제레포1 B 에선 3건이 없어 신규 작성 후 삭제).
- 무손실의 가장 싼 증거는 **`[[포인터]]` 링크 차집합 양방향**. 그 다음이 규칙 앵커 목록 대조.
- ⚠️**앵커 대조를 `grep` 으로 기계 판정하지 마라 — 백틱·띄어쓰기 차이로 위양성이 쏟아진다**(형제레포1 B 에서 재현: 63건 중 실손실 0인데 전부 MISSING 으로 찍혔다). 차집합은 *후보 목록*으로만 쓰고 판정은 항목별 전문 대조로 한다.
- **게이트 임계는 바이트고 한글은 3바이트/자다.** 문장 병합·재배열은 거의 효과가 없다(줄 병합 1건 = 5바이트) — **문구를 실제로 지워야** 준다.
- **임계 바로 아래에서 멈추지 마라**(7B 여유면 다음 규칙 한 줄에 바로 걸린다). 100B 이상 여유를 두고 끝낸다.
- **판정 실례** — 남긴다: 규칙 문장·그 레포 고유 판정축·도메인 표준값·접속/포트/경로·상시 쓰는 실행 명령. 밀어낸다: 실사고 서사·실측 수치·"왜 이 규칙이 생겼나"·형제 레포 비교·스킬이나 원문 문서가 이미 가진 체크리스트. 전역과 원리가 겹치면 프로젝트엔 "정본 = 전역" + 그 레포 계약만.

⚠️**청소보다 배수구가 먼저다.** A/B 는 일회성이고, 증가 속도를 안 잡으면 원위치한다(같은 패턴이 `agent_history.md` 에서 40KB 임계를 21회+ 넘긴 이력으로 이미 실증됐다). 그래서 배치 규칙 ④ + 크기 게이트를 먼저 세우고 청소했다.

⚠️**게이트를 자기 편의로 조정하지 마라.** 배수구 규칙을 전역에 넣자 전역이 25.3→26.7KB로 **상한을 넘었다**. 임계를 올리는 대신 그 항목을 규칙대로(3줄 초과 → 서사는 memory) 줄였고, 그래도 남는 초과는 **"전역 축소가 필요하다"는 정직한 신호로 남겼다.**

**게이트 해제(2026-08-13, 사용자 결정 — 위 조항과 구분할 것):** `rules-size-check.sh` Stop 등록을 전역 settings.json 에서 제거. 근거 = 배치 규칙 ④(배수구)가 정착됐고, 압축의 실이득이 작았다(2KB ≈ 토큰 1k ≈ 상시 로드의 3% — 2026-08-13 스윕 실측: 인덱스 12.9→12.3KB 에 편집 20여 회). "자기 편의 조정 금지"는 **에이전트가 임의로** 임계를 만지는 것을 막는 조항이고, 이번 건은 사용자 지시라 다른 축. 스크립트·킷 회귀 케이스는 보존(원복 = Stop 재등록). 배치 규칙·축소 절차(A/B/C·사용자 승인)는 계속 유효.
