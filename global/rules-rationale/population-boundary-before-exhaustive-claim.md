# 전수/모집단 주장 전 경계 선언 — 근거

## 무엇 (전역 CLAUDE.md grep 조항 ⑥의 정본)
"전수 확인했다"·"모집단 X건"을 근거로 쓰기 전에 ⓐ모집단 경계(트리·확장자·변경종류 D/M/A/R) ⓑ소유 축(예: 퍼블 vs 개발) ⓒ그 경계를 만든 명령(find/grep 커맨드라인 자체)을 먼저 적는다. grep 5가지 판정의 ①(분모 확인)이 "개수가 맞는가"를 다룬다면, 이건 "**분모를 정의한 경계 자체가 맞는가**"를 다룬다 — 다른 실패축이라 별항으로 승격.

## 왜 (실측 경위)
2026-08-25 예시 레포 디렉토리 재편(정적자원+템플릿+매퍼 경로 통합) 단일 작업에서 **같은 형태의 오류가 3회 반복**됐다:

1. **복구 분모를 D로만 잡음** — 삭제된 파일(D) 목록만으로 "복구 완료"를 판단했으나, 실제로는 팀 병합이 우리 개발 JS 12개를 **덮어쓴(M)** 것도 있었다. `git diff --diff-filter=D`만 보고 `--diff-filter=M`을 안 봐서, 사용자가 결함을 먼저 잡을 때까지 몰랐다.
2. **삭제 판정에서 소유 축을 안 가름** — "이 디렉토리는 이제 안 쓴다"는 판단을 퍼블/개발 소유 구분 없이 트리 단위로 내렸다가, 사용자가 "퍼블팀 관련 산출물은 유지해야 한다"고 제동했다.
3. **주석 드리프트 분모를 개발 JS 파일종만 잡음** — "이 API를 설명하는 주석을 다 고쳤다"를 개발 소유 `.js` 파일에서만 확인했고, 같은 API를 설명하는 **템플릿(`.html`) 내 인라인 주석 3건**을 분모에서 빠뜨려 리뷰가 CONFIRMED로 잡았다.

세 건 모두 **개수 세는 방법(grep/diff 커맨드 자체)은 정확**했다 — 명령은 옳게 실행됐고 결과도 정확히 읽었다. 틀린 것은 "그 명령이 어떤 모집단을 커버하는가"를 사전에 명시하지 않은 것이었다. 즉 grep 5가지 판정의 ①~⑤는 "명령·개수가 옳은가"를 검증하지만, 이 사고들은 **명령 자체는 옳은데 그 명령이 정의하는 경계가 좁았던 경우**라 기존 5가지로는 안 걸린다.

## 승격 판단 근거
프로젝트 memory `promotion-candidates.md`의 "3회 도달 = 승격 검토" 규칙에 따라 2026-08-25 한 작업 내 3회 반복 시점에 마킹됐고, 2026-08-26 사용자 승인으로 전역 규약 grep 조항 ⑥으로 승격했다. 방법론(모집단 경계 선언)은 스택 무관이라 전역 배치(배치 3규칙 ①) — 레포별 구체 사례는 [[static-asset-merge-loss]](예시 레포 memory)에 보존.

## 적용 시점
"전수"·"모집단 N건"·"다 고쳤다"·"복구 완료" 류의 주장을 리뷰·보고·커밋 사유에 쓰기 직전. 표본 1개 일반화 금지 조항과 자매 조항 — 그쪽이 "몇 개를 보고 하는 말인가"를 묻는다면 이쪽은 "그 몇 개를 셀 때 경계를 어디로 그었는가"를 묻는다.


## 경위(2026-09-17 이동)

**상태주장:3 축약(원문 전문 — grep 6판정):** grep 은 존재 증명에 강하고 부재 증명에 약하다.
①**0 은 분모(모집단) 먼저**(분모 0 = "해당 없음") ②**양성 대조**로 패턴이 살아 있음을 확인 ③벤더·백업·산출물 트리 제외 + hit 소유 경로 확인 ④**`head`/`tail` 없이 `grep -c`·`wc -l` 로 다시 센다** ⑤**명령 실패와 결과 0 을 구분**(zsh 미인용 글롭은 명령을 통째로 죽인다 — 글롭·변수는 항상 인용, exit code 를 본다) ⑥"전수"는 개수가 아니라 **경계**(트리·확장자·변경종류 D/M/A/R·소유 축)를 먼저 적는다.
부재 주장은 grep 한 축으로 끝내지 말고 Read·LSP·교차표로 교차한다. ⑤의 일부는 기계화 가능(grep exit≥2 경고 — 승격 대기), ①②는 의미 판정이라 불가.
