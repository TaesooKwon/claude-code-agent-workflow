  - **⚠️`grep` 결과를 근거로 쓸 때의 6가지 판정(하루에 오탐 3건이 난 실측 뒤 고정, 2026-08-19 ④ 추가, 2026-08-26 ⑥ 추가):** grep 은 **존재 증명엔 강하고 부재 증명엔 약하다.** "0건이니 없다"를 주장의 근거로 삼기 전에 아래를 통과시킨다.
    - **①0 은 분모를 확인하기 전엔 의미가 없다** — "위반 0"과 "모집단 0"이 같은 `0` 으로 보인다. 실측 사고: 어떤 레포에 가드 패턴이 0건이라 "가드가 없어 취약"이라 단정했으나, 실제로는 **그 API 호출부 자체가 0건**이라 취약할 코드가 없었다. ⇒ **위반 수를 세기 전에 모집단(그 API·패턴을 쓰는 지점) 수를 먼저 센다.** 분모가 0이면 결론은 "안전"도 "취약"도 아닌 **"해당 없음"**이다.
    - **②패턴이 실제로 매칭되는지 양성 대조를 먼저 한다** — 0 이 "없어서"인지 "패턴이 틀려서"인지 구분되지 않는다. 실측 사고: 백틱이 낀 문구(`` `X` 를 ``)를 백틱 없이 검색해 0 을 얻고 "미반영"으로 보고했다(실제로는 반영돼 있었다). ⇒ **반드시 존재한다고 아는 인접 문자열로 1회 매칭시켜 grep 이 살아 있음을 확인**한 뒤 부재를 주장한다(테스트 반증검사와 같은 축).
    - **③벤더·백업·산출물 트리를 제외하고, hit 는 소유 경로인지 확인한다** — 실측 사고: 팀 공통 래퍼를 찾는 grep 이 `lib/jquery.js` **내부 함수**에 걸려 "팀 래퍼 있음"으로 오판했다. ⇒ `--exclude-dir` 로 `lib`·`node_modules`·`target`·`dist`·백업 트리(`*-old`)를 빼고, 남은 hit 도 **파일 경로를 보고 우리 소유인지** 확인한다(이름만 보고 판단 금지).

- **로직엔 단위테스트 기본 (검증 자동화 — 값어치 나는 곳만):** 로직 있는 변경(분기·계산·필터·상태전이·서비스 배선/상호작용)엔 단위테스트를 **기본으로 붙인다** — 외부의존 없이 격리 검증이라 싸고 결정적이고, 런타임 왕복보다 회귀가 강하다. **제외(과잉 금지)**: 단순 위임/CRUD 패스스루엔 테스트할 로직이 없고, 외부의존 경계(DB·네트워크·파일·렌더)는 통합/E2E가 맞다. 도구·프레임워크는 스택별(프로젝트 규약이 지정 — 예 Java=Mockito JUnit5). 방법론은 범용이되 적용은 선별 — 위임·도구 경제와 정합(테스트도 값어치 나는 곳에만). 능동적으로 붙이되 얇은 코드엔 억지로 달지 않는다. 〔+Claude 2026-07-25〕
  - **경합이 있는 기능은 두 컨텍스트 동시 조작 E2E 가 필수다(하한선 ② 의 경합 축):** 폴링·동시 저장·상태전이·채번·커서가 있으면 브라우저 컨텍스트 2개(또는 병렬 요청)로 **동시 전송·교차 갱신** 시나리오를 E2E 에 넣는다. 리뷰·단위테스트는 단일 흐름만 본다 — 실측: 다관점 리뷰 3회가 전부 놓친 폴링 커서 결함(동시 전송 표시 유실)을 E2E 1회가 잡았다. 절차 = `playwright-verify` 스킬 5-3절. 〔+Claude 2026-09-03〕

- **검증의 무게는 diff의 성격에 비례시켜라 (리스크 티어링 — 크기가 아니라 성격):** 모든 변경에 같은 무게의 게이트를 균일 적용하면, 결함이 있을 수 없는 곳에 시간을 쏟고 정작 위험한 변경과 구분이 사라진다. **실측(2026-08-06)**: 템플릿 마크업 23줄 변경에 다각 리뷰 15에이전트·1.08M 토큰·9.5분 → CONFIRMED 0, 3줄 클래스 교체에 6에이전트·402k 토큰·5.8분 → CONFIRMED 0. 두 번 다 나온 지적은 전부 **diff 밖 기존 성질**이거나 **공통자산이라 손댈 수 없는 것**이었고, 후자는 지적자가 스스로 "이번 diff의 결함이 아니다"라고 적었다. 반면 같은 무게가 JS 상태·비동기 재진입 변경에서는 되돌릴 수 없는 오작동(확인 모달 재진입으로 [확인]이 제출을 실행)을 잡았다. **가른 것은 diff의 크기가 아니라 성격이다.**
  - **A티어(무거운 리뷰 유지) = 실행 의미가 바뀌는 변경**: 서버 코드·DB 접근·인증/인가·상태 전이·비동기/이벤트 배선·조건 분기 신설. **B티어(셀프리뷰로 강등) = 표현만 바뀌는 변경**: 마크업 클래스·문구·스타일 교체이면서 **데이터 바인딩·분기·핸들러가 무변경**일 때.
  - **판정은 기계적 축으로**(주관 금지): staged diff 에 ①로직 소스파일 ②데이터 접근 정의(쿼리·매퍼) ③인라인 스크립트의 **동작** 변경 ④조건·반복 바인딩 **신설** 중 **하나라도** 있으면 A. 스택별 구체 확장자·문법 축은 프로젝트 규약이 지정한다.
  - **소형 A = 단일 에이전트 델타형 리뷰(A-라이트 폐지, 2026-09-03):** A 판정이되 ⓐ스테이징 ≤5파일 ⓑ인증/인가·상태전이·비동기 배선·신규 스키마 **무변경** ⓒ변경 로직을 단위테스트가 직접 커버 — **셋 다**면 다각 워크플로 대신 **에이전트 1개**(세션 모델)에 behavior+regression 을 한 프롬프트로 주고, 결과를 **CONFIRMED 제목·파일·라인 1:1 수리 체크리스트**로 받아 적는다. 하나라도 미충족이면 풀 A. 경량 실행했음을 사용자에게 보고. 근거 = 2관점 워크플로(옛 A-라이트)는 47만 토큰에 LOW 2 로 저수익이었고, 델타형 단일 리뷰가 BLOCK 1·수리가 만든 결함 2 를 잡았다([[review-alite-dedup]]).
  - **verify 는 지적을 병합해 고유당 1회 판정하고, 실행은 파일 단위로 배치한다**: 다관점의 가치는 "찾기"의 다양성이지 같은 지적의 재검증이 아니다(실측: CONFIRMED ~195건 중 고유 ~109건 — verify 의 44% 가 중복이었다). ⚠️**병합 키를 `(file, 라인)` 정확일치로 두면 절감이 0 이다** — 관점마다 같은 결함을 다른 라인으로 인용한다(실측 `:1291` vs `:1010 부근`). ⇒ 라인 근접·제목 유사로 완화하되 **서로 다른 관점 사이에서만** 병합하고, 지적이 몰린 파일은 **에이전트 1개가 독립 판정 블록으로** 처리해 파일 재독을 없앤다. **배치의 대가 = 에이전트 1개 사망이 그 파일 지적 전부를 삼킨다** ⇒ 미판정은 기각으로 접지 말고 **게이트를 막아라**(2026-08-28). **verify 모델 하향·델타 재리뷰 생략은 금지** — 진짜 지적을 verify 가 기각해 메인 세션이 뒤집은 실사례, "수리가 절반/수리가 새 결함" 을 델타 재리뷰가 잡은 실사례가 있다.
  - **강등의 조건 4가지(하나라도 빠지면 티어링이 아니라 검증 포기)**: ⓐ**애매하면 A**(오분류 비용이 재검 비용보다 훨씬 비싸다) ⓑ**B도 빌드·렌더 검증은 그대로**(줄이는 것은 다각 리뷰 하나뿐) ⓒ**B로 판정했음을 사용자에게 말한다**(침묵 강등 금지 — 규칙이 아니라 구멍이 된다) ⓓ**게이트 마커·지문 대조는 티어 무관 유지**(수정 시 마커가 무효화돼 재검이 강제되는 구조가 실제로 결함을 잡았다).
  - **검증은 직렬이 아니라 병렬**: 렌더/E2E 검증과 리뷰는 둘 다 읽기전용이라 **동시에** 띄운다(직렬로 돌면 체감 시간이 2배). 같은 세션에서 이미 확인한 화면·경로는 재검증하지 않는다.
  - **리뷰 위임 스키마에 "그 지적이 걸리는 변경 라인"을 필수 필드로 넣어라**: "diff 밖은 보고 금지"를 프롬프트로 써도 계속 새어 나온다(실측 10건 중 대부분). 필수 필드로 만들면 스코프 밖 지적이 **구조적으로** 생성 불가가 되고, 그것을 반박하는 verify 비용도 함께 사라진다. 〔+Claude 2026-08-06〕
  - **리뷰 지적을 수리했으면 반드시 재스테이징한다 — 순서는 수리 → `git add` → 델타 재리뷰 → 빌드·검증 → 마커 → 커밋.** `git add` **이후**의 편집은 인덱스에 안 들어가므로, 재스테이징을 빼먹으면 **리뷰 전 코드가 그대로 커밋된다**(수리한 줄이 워킹트리에만 남는다). 리뷰 마커의 지문도 **인덱스 기준**이라 재스테이징 전에 마커를 찍으면 지문이 어긋나 게이트가 그대로 막는다 — 게이트가 잡아주긴 하지만, 그 전에 순서로 지키는 게 맞다. 〔+Claude 2026-08-07〕
  - **병행 세션과 워킹트리·인덱스를 공유할 땐 ①일괄 스테이징 금지(`git add -A/--all/-u/.`·`git commit -a`) ②리뷰는 worktree 에서 선실행, 메인에서는 재스테이징·마커·커밋만**(사용자 확정 2026-09-02): `git commit` 은 인덱스 전체를 가져가므로 내 `git add` 가 남의 커밋에 휩쓸리고, 상대 커밋을 기다렸다 리뷰하면 리뷰 시간이 직렬로 붙는다. 처방 = 내 변경만 복사한 worktree 에 스테이징해 리뷰 워크플로를 `args.repo` 로 돌리고, 상대 커밋이 HEAD 에 들어온 뒤 메인에서 같은 경로를 `git add` → `git diff --cached | grep -v '^@@'` 로 리뷰 diff 와 대조 → 마커 → 커밋. ①은 PreToolUse 훅 `git-add-all-guard.sh`(킷 스캐폴드·`ALLOW_GIT_ADD_ALL=1` 예외)로 강제한다. 절차·스크립트·실측 = [[parallel-session-shared-index]] 〔+Claude 2026-09-02〕
  - **델타 재리뷰는 새 워크플로가 아니라 단일 에이전트 1개로 — 1차 지적·수리 주장을 전사해서 준다.** 워크플로의 finder/verify 에이전트는 주소가 없어 `SendMessage` 로 이어 붙일 수 없다(옛 문구 정정, 2026-09-03 실측). 프롬프트에 ①원 지적(제목·파일·라인) ②수리 주장(무엇을 어떻게) ③수리 diff 를 박고 "수리가 절반인가·수리가 새 결함을 만들었나·기각된 지적은 다시 올리지 마라"를 지시한다. 템플릿 = 프로젝트 `.claude/workflows/delta-review.md`. 수리 델타는 대개 수 줄이라 다각 팬아웃은 과잉이다 — 위임·도구 경제와 같은 축. 〔+Claude 2026-08-07 /~2026-09-03〕

- **전체 E2E 회귀 스위트 = 온디맨드(커밋 게이트 금지):** 누적 회귀 스위트의 **전량 실행은 사용자가 요청할 때만**(시간·토큰 여유, spec 축적 후 일괄 검증 등 실행 시점 판단은 사용자 몫) — 커밋 훅 게이트·마커 강제로 두지 않는다. 근거(실측 2026-08-07, 형제레포1·예시 레포 게이트 해제): 스위트는 개발이 쌓일수록 자라(29·71케이스) 게이트 비용이 선형 증가하는데, 적발 실적은 전부 **파급을 예측하기 어려운 무거운 변경**(설정/properties·인증/세션·DB 스키마·공통 모듈)에서 나왔고, 표현성 변경에서는 적발 0에 무관 빨간불(스펙 낙후·환경 드리프트·플레이크) 트리아지 비용만 남았다. 운용: ①커밋 상비 게이트 = 빌드/하네스·단위테스트·자체 리뷰(티어링)까지 ②위 무거운 축을 커밋할 땐 전량 회귀 실행을 **제안**(실행은 사용자 승인 시) ③변경 관련 spec 서브셋 실행은 에이전트 재량 ④전량 회귀의 정석 자리는 커밋 게이트가 아니라 주기 실행/CI. 〔+Claude 2026-08-07〕

- **테스트는 "통과"가 아니라 "실패할 수 있음"을 확인하라 (반증검사):** 새로 쓰거나 고친 테스트·단언은 **고의로 기대값을 어긋나게 만들어 실제로 빨간불이 뜨는지** 1회 확인한다. 방어적 `if (있으면 확인) else (로그만 남김)` 구조는 셀렉터·경로가 썩어도 영원히 통과해 회귀 게이트에 구멍을 낸다(실측: 저장 버튼도 폼 필드도 못 찾은 채 통과하던 E2E 스펙 — 호출하던 API 경로 자체가 존재하지 않았다). 부수 원칙 ①셀렉터·경로는 실물(컨트롤러·템플릿)을 읽고 실제 응답을 찍어 확정(추측 금지 — 상태주장 검증 규칙과 같은 축) ②화면뿐 아니라 **응답 계약**(HTTP 메서드·status·응답코드)까지 단언 ③응답을 믿지 말고 **저장값을 재조회**해 확인 ④필터·검색은 **양성+음성**(없는 값 → 0건) 양방향 반증 ⑤상태를 되돌리는 정리 코드는 별도 테스트가 아니라 **teardown 훅**에 둔다(별도 테스트로 두면 앞 테스트가 실패한 실행에서 안 돌아 dev DB가 오염된다 — 실측 사고). 〔+Claude 2026-07-28〕
  - **⚠️부칙 — 반증검사 자체가 거짓을 말할 수 있다(하루에 서로 다른 세션이 정반대 방향으로 각각 밟았다, 2026-08-20).** 반증검사는 안전망의 안전망인데, **"빨간불이 안 떴다"가 두 가지 다른 뜻**일 수 있다: *결함을 못 잡는다*(거짓 초록)와 *검사가 아예 안 돌았다*(미실행). 이 둘을 구분하지 않으면 멀쩡한 테스트를 의심하거나 뚫린 테스트를 믿는다.
    - **ⓐ변이가 실제로 적용됐는지 먼저 단언하라** — 치환 스크립트는 **매치 건수를 `assert`** 하고, *매치 실패*를 *테스트 통과*와 분리해 보고한다. 실측: 파일엔 소스 이스케이프(` ` 6글자)가 있는데 검색어는 실제 문자라 매치 0건 → 변이가 안 걸린 채 "통과"로 보였다. 부수로 **비가시 문자(NBSP·제로폭)는 소스에 리터럴로 넣지 말고 이스케이프로 박아라** — 도구·에디터가 정규화하면 가드가 조용히 사라지고 테스트에도 똑같이 반영돼 초록으로 위장된다.
    - **ⓑ메시지 근거 단언은 그 메시지가 유일한 경로에서만 나오는지 확인하라** — 부분문자열 대신 **전문 일치·구조적 단언**. 실측: 매직바이트 가드를 지웠는데 `getMessage().contains("엑셀")` 이 라이브러리의 *다른* 실패 메시지("엑셀 파일을 여는 중 오류…")에도 걸려 초록을 유지했다.
    - **ⓒ변이 결과가 예측과 일치하는지 본다** — 몇 건이 왜 깨져야 하는지 먼저 적고 대조한다. 안 깨진 것이 **정상통과 케이스**인지 **사각**인지는 그 대조로만 갈린다.
    - **ⓓ변이 실행 결과에 `Tests run: N>0`(스택 상당물)을 단언하라** — 컴파일 실패·미실행은 "미반증"이지 통과가 아니다. 변이는 **컴파일되는 형태**(상수·비교연산자·분기 조건 반전)로 만들고, 보고에 실행 건수를 적는다. 실측: 컴파일 불가 변이가 안 돌았는데 통과처럼 보고됐다(2026-09-03).
  - **⑥결함이 특정 층에만 사는 종류면 검증도 그 층에서 해야 한다.** 목(mock) 테스트는 그 위 레이어만 보므로 **아래 층에만 존재하는 결함을 원리적으로 못 잡는다** — 실측: 매퍼 XML 이 `SITE_IDNTF_NO = #{userIdntfNo}`(사이트 자리에 사용자 ID)로 **실데이터를 오염시키는 동안 모든 테스트가 초록**이었다. SQL 텍스트에만 사는 결함은 **렌더된 SQL 문자열을 단언**해야 잡힌다(스택별 상당물: ORM 이 만든 쿼리, 생성된 마이그레이션, 빌드 산출물). 정적 lint 는 문법 룰을 보지 **어느 컬럼에 무엇을 넣는지는 보지 않는다** — 둘은 다른 층이다. 〔+Claude 2026-08-20〕
