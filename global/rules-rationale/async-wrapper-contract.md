## ①재진입(in-flight) 가드 — 왜 "조용한 데이터 소실"인가

공통 ajax 래퍼는 대개 in-flight 레지스트리도 클릭 차단도 없는 **순수 래퍼**라 연타를 아무도 막지 않는다.

**"더보기 누적" 페이징의 실패 경로**: 페이지 번호가 응답 콜백에서만 갱신된다 → 응답 전 재클릭 → **같은 page 를 두 번 요청** → 같은 항목이 두 벌 append → 누적 카운트가 부풀어 `누적 >= 전체` 가 조기 성립 → **더보기 버튼이 사라지고 뒷 페이지에 영영 도달 못 한다.** 에러도 경고도 없이 데이터가 사라지는 형태라 실사용 전에는 안 보인다.

해제를 **성공·실패 양쪽**에 거는 이유: 한쪽만 풀면 실패 후 영구 잠금. 제출 버튼도 같은 축이다.

## ②래퍼의 실패 계약 — 세 갈래, 처방이 정반대

### ⓐ sentinel 을 콜백에 넘기는 계약

래퍼가 401/403/500 을 자체 처리하고 성공 콜백에 `false` 같은 sentinel 을 넘긴다. 구분하지 않고 일반 실패 문구를 띄우면 **안내가 두 겹으로 뜨거나(중복) 앞 안내가 덮여 사라진다(소실)**.

어느 쪽이 되는지는 **다이얼로그 구현**이 가른다:

| 구현 | 재진입 결과 |
|---|---|
| 싱글턴 재사용 (앞 호출을 취소하고 본문 교체) | 앞 메시지가 **덮여 사라지고**, 앞 Promise 를 기다리던 호출부 로직까지 조용히 중단 (**정보 + 콜백 소실**) |
| 호출마다 새로 만들어 append 후 `showModal()` | 두 개가 **스택될 뿐 앞 메시지는 보존**(위를 닫으면 아래가 드러남). 대신 중첩 모달이라 포커스 트랩·ESC 가 탁하다 |

⇒ **정보·콜백 소실이 시각적 잡음보다 나쁘다.** 근본 해법 = 싱글턴을 유지하되 재진입을 덮어쓰기가 아니라 **큐잉**으로.

⚠️ 래퍼 내부의 `alert` 이 `window.alert` 이 아니라 **같은 스코프의 커스텀 다이얼로그**(비블로킹)인 경우가 흔하다 — 네이티브로 착각하면 "블로킹이라 안 겹친다"는 **잘못된 반증**을 하게 된다(실제로 그렇게 오판했다).

### ⓑ 실패 시 콜백을 아예 안 부르는 계약 — 영구 잠금

**실측 2026-08-11 (형제레포1)**: 팀 커밋이 BO 래퍼의 `.then` 가드를 `if(response !== false && response != null && typeof handler === 'function')` 로 바꿨다. 결과로 401/403/413/500 시 **handler 가 호출되지 않고, 4번째 인자 error 콜백도 `.catch` 경로라 안 탄다.**

- `resp === false` sentinel 가드가 **도달 불가능한 죽은 코드**가 된다.
- 더 나쁜 것: 버튼을 잠근 뒤 **handler 안에서만 푸는 화면은 실패 시 해제 코드가 실행되지 않아 새로고침 전까지 버튼이 죽는다.** ①의 "성공·실패 양쪽에서 해제"가 정확히 이 축인데, 콜백이 하나뿐인 래퍼에서는 "양쪽"이 성립하지 않으므로 **해제를 콜백 밖에 둬야** 한다.
- 확증 사례: 관리자 로그인 화면의 인증서 로그인 경로 — 잠금 1곳, 해제는 전부 handler 내부.

### ⓒ 래퍼가 없는 레포 (`$.ajax` 직접 호출)

해당 없음. 착수 전 그 레포에 래퍼가 있는지부터 본다.

### 계약은 레이어별로 갈리고, 팀 커밋 한 방에 바뀐다

- **레포가 아니라 레이어가 축이다** — 2026-08-07 두 레포 교차 실측에서 **FO 끼리, BO 끼리** 같았다(FO 싱글턴 취소형 / BO 매번 생성형).
- **같은 레포 안에서도 갈린다** — 2026-08-11 팀 커밋은 **BO 만 ⓐ→ⓑ로 바꾸고 FO 는 그대로 뒀다.** 한 레포에 두 계약이 공존하게 됐다.
- ⚠️ 형제 레포 문구를 그대로 베끼면 틀린다(이 항목은 그렇게 하다 **2회 정정**됐다).

**Why:** 계약을 잘못 가정하면 처방이 정반대로 간다 — ⓑ에 ⓐ의 처방(콜백 안 가드)을 쓰면 아무 일도 일어나지 않고 버튼만 죽는다.

**How to apply:** 착수 전 그 **레이어**의 래퍼를 실물로 열어 ⓐ/ⓑ/ⓒ를 판정한다. 공통 래퍼가 바뀐 팀 커밋이 유입되면 **잠금을 거는 화면들을 함께 훑는다**(모집단부터 세고 — [[verify-state-claims-before-asserting]] grep 4판정 ①).

## ③라이브 리전 재낭독

`role="status"`·`aria-live` 요소에 매 응답마다 `textContent` 를 재대입하면 **값이 그대로여도** 텍스트 노드 교체가 변경으로 통지된다. 목록 누적처럼 **새 항목으로 포커스를 옮기는 경로**와 겹치면 이중 낭독. 값이 바뀔 때만 대입하면 검색은 정상 낭독되고 더보기는 침묵한다.

반대 방향도 있다: 비동기 검색은 포커스가 [검색] 버튼에 남아 결과 교체가 **아예 통지되지 않으므로** 0건·조회실패 박스에는 `role="status"` 를 걸어야 한다.
