# 상시 결함 사냥꾼

## 결정(사용자, 2026-10-10 예시 레포 세션)
- 사용자: "오류만 찾아내는 에이전트도 하나 추가하는거 어때?" → "상시로 넣으면 좋지 않을까??" → 배치안 승인("결함 사냥꾼 승인").
- 배치 = 이미 매번 도는 관문 두 곳에 끼운다(새 관문을 만들지 않는다):
  1. **커밋 리뷰 `attack` 관점** — `.claude/workflows/commit-review.js` LENSES 5번째. A티어 커밋마다 자동(heavy 모드면 cr-api 로 API 크레딧).
  2. **설계 컨펌 전 병행** — 인증·인가 / 경합 자원 / 데이터 삭제·이관을 건드리는 설계일 때만, 사실 반증자와 별개로 공격·실패 시나리오만 찾는 검증자 1개.
- 모든 작업에 붙이지 않는 이유: B티어·단순 CRUD 설계엔 비용 대비 잡음. "검증 무게는 diff 성격에 비례" 축과 같다.

## 설계 단계 고정 항목 — 부작용 사냥(사용자 승인 2026-10-14 예시 레포)
- 설계 컨펌 전 사냥꾼은 공격 시나리오와 함께 **부작용 사냥**을 반드시 한다. 커밋 단계는 commit-review.js `regression` 관점이 같은 축을 맡으므로 손대지 않는다.
- 이유 = 설계가 바꾸는 **전제**(예: "첫 요청에 세션이 있다")에 기대던 기존 코드는 공격 축 체크리스트로는 안 보이고, 커밋 리뷰에서야 잡히면 구현·테스트·변이·델타 재리뷰가 한 바퀴 더 돈다.
- 사냥꾼 프롬프트에 그대로 전사하는 골격:
  ```
  [부작용 사냥]
  ① 이 설계가 바꾸는 상태·전제를 먼저 나열하라(세션·토큰·요청 속성·호출 순서·기본값·응답 형태 등 — "지금까지 늘 참이던 것" 중 이 변경 뒤 거짓이 될 수 있는 것).
  ② 그 전제에 기대는 기존 코드를 grep 으로 찾아라(예: getSession(false) 가드, 요청 속성 소비처, 같은 상수·헤더 소비처). 모집단 명령과 건수를 적어라.
  ③ 정상 사용자 흐름에서 동작이 달라지는 곳을 "누가(역할·로그인 여부) → 어떤 흐름 → 어떻게 달라짐(늦어짐·누락·403·루프)" 형식으로 적어라. 공격자가 없어도 생기는 변화만 이 절에 쓴다.
  ```

## 기존 규칙과의 관계
- commit-review.js 헤더의 "새 점검 축은 관점을 늘리지 말고 기존 관점 항목으로 접는다"(2026-10-09)의 **명시적 예외**. 이유 = 결함만 찾는 공격자 시점은 "의도대로 동작하나"를 보는 behavior·regression 항목으로 접으면 희석된다. 사용자가 '별도 에이전트'를 요청했다.
- 지적은 기존처럼 적대적 verify(기본값 = 기각)를 통과한 것만 CONFIRMED. failureScenario 는 "누가 → 어떤 요청 → 어떤 잘못된 결과" 형식 강제(일반 권고 차단).
- cr-api.mjs 선확인 예산을 finder × 5 로 올렸다(관점 수가 레포마다 다를 수 있어 큰 쪽).
