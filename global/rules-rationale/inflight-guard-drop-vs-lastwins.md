비동기 재진입 가드를 붙일 때 **요청의 성격을 먼저 가른다.**

| 성격 | 처방 | 이유 |
|---|---|---|
| **제출·생성·삭제**(부작용 있음) | **드롭** — `if(loading) return;` | 중복 실행 방지. 같은 역할이 두 번 등록되면 안 된다 |
| **조회성 재렌더**(화면을 갈아끼움) | **last-wins** — 시퀀스 토큰 | 드롭하면 **사용자가 최종적으로 고른 것이 버려진다** |

**Why:** 2026-08-14 실측 — 역할관리에서 소속 사용자유형 select 를 바꾸면 접근메뉴 트리를 다시 받아
갈아끼우는데, 여기에 제출용 드롭 가드를 그대로 썼다. 닫힌 native select 를 키보드로 훑으면
**옵션마다 change 가 발사**되므로 첫 요청이 진행 중인 동안 **마지막에 착지한 선택이 통째로 드롭**된다.
결과 = select 는 관리자인데 트리는 프론트가 남고, 그 상태로 저장하면 서버가 영속 유형으로 축을
재계산해 전건이 거부된다. 커밋 전 A티어 리뷰에서 **4개 관점이 독립적으로 같은 결함을 잡았다.**

전역 규약의 "비동기 3대 재발 결함 ①재진입 가드" 조항은 **제출 축만** 다루고 있어(더보기 페이징·제출 버튼)
그 반대 축을 그대로 밟았다. 조항이 틀린 게 아니라 **적용 범위를 내가 잘못 넓혔다.**

**How to apply:**
1. 가드를 붙이기 전에 **"이 요청은 부작용이 있나"**를 묻는다. 없으면 드롭이 아니라 last-wins.
2. last-wins 구현 = 모듈 스코프 `let seqCounter = 0;` → 진입 시 `const seq = ++seqCounter;` →
   **응답 적용 직전** `if(seq !== seqCounter) return;` 로 낡은 응답만 폐기. 요청 자체는 막지 않는다.
3. **`aria-busy` 해제도 최신 요청일 때만** 한다 — 낡은 응답이 해제하면 아직 진행 중인데 완료로 보인다.
   단 **성공·실패 양쪽에서 해제**하는 계약은 그대로(한쪽만 풀면 실패 후 영구 잠금).
4. ⭐**비동기 응답에서 화면을 다시 읽어 안내 문구를 만들지 마라** — 요청 시점 값을 캡처한다.
   응답이 올 때쯤 select 는 이미 다른 값일 수 있고, `role="status"` 는 그 어긋남을 **소리로** 내보낸다
   (틀린 유형명이 낭독된다). 값으로 옵션을 찾는 헬퍼를 두고 요청 시점에 호출한다.
