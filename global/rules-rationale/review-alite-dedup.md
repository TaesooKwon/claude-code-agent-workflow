> ⚠️ **2026-09-03 A-라이트 폐지** — 2관점 워크플로 경량 실행은 저수익(47만 토큰에 LOW 2, 5회 전부)이라 폐지하고, 같은 조건(≤5파일·위험축 무변경·테스트 커버)은 **단일 에이전트 델타형 리뷰**(`delta-review.md` 템플릿)로 대체했다. 아래는 폐지 전 근거·verify 병합 원리(후자는 유효).

전역 조항(리스크 티어링 절의 "A-라이트"·"verify 병합") 정본 근거. 2026-08-27, 예시 레포
`docs/agent_history.md` + 백업 10개(08-13~08-27)에서 **커밋 리뷰 실행 24회를 전수 추출**해 확정했다.

## 실측 3가지

1. **중복 verify 44%** — 24회 합계 CONFIRMED ~195건 중 고유 ~109건. 관점(behavior/markup/a11y/
   regression)들이 같은 결함을 각자 보고했고, 병합 로직이 없어 **중복 지적마다 적대 verify 에이전트가
   따로 돌았다**(회차 예: 17건=고유 8 · 14건=고유 7 · 18건=고유 11 · 11건=고유 5). 다관점의 가치는
   "찾기"의 다양성이지 같은 지적의 재검증이 아니다 → verify 앞 (file, changedLine) 병합으로 소거.
   비용 실측: 풀 리뷰 1회 = 13~26에이전트 · 1.15~2.6M 토큰 · 13~17분.

2. **저소득 회차의 공통 형태** — CONFIRMED 0~1건(LOW)로 끝난 5회(WP0 0건 / 커밋③ 페이지화 LOW 1 /
   MbrMapper 4파일 0건 / MENU_ID 주석 1 / 고교한정 주석 2)는 전부 **소형 diff + 두꺼운 단위테스트 +
   위험축(인가·비동기·상태전이·신규 스키마) 부재**였다. **반례 검산**: 선이수 리뷰는 CONFIRMED 1건뿐인데
   그게 🔴 레이스("확인한 수업과 다른 수업에 신청")였다 — 그 diff 는 비동기 배선 변경이라 A-라이트
   조건 ⓑ에서 걸러져 풀 A 유지. 판정축이 반례를 통과한다.

3. **자르면 안 되는 것 2개(강화 방향의 실측)** —
   - **verify 모델 하향 금지**: 08-26 매퍼 게이트 리뷰에서 verify 가 **진짜 지적을 기각**했고 메인
     세션이 뒤집어 수리했다(메인 모델 verify 에서도 발생). verify 는 기본값이 기각이라 약화가 위험
     쪽으로만 쏠린다. 최초 권장안의 "A-라이트 verifyModel: sonnet"은 이 실측으로 **철회**됐다.
   - **델타 재리뷰 생략 금지**: "수리가 절반만 됐다" 실측 3회(대리등록 델타 6건=실질 3 · WP2.3 델타
     7건), **수리가 새 결함을 만든 것**을 잡은 실측 2회(권역 관리).

## 처방(전역 조항 요지)

- **A-라이트** = A 판정 diff 중 ⓐ≤5파일 ⓑ위험축 무변경 ⓒ로직 테스트 커버 → finder 를
  behavior·regression 2관점으로. 모델·verify 무게·델타 재리뷰·마커는 그대로. 침묵 강등 금지.
- **verify 병합** = 관점 지적을 병합해 고유당 1회 판정. 같은 라인의 다른 결함 2개가
  합쳐질 위험은 지적 전문을 verify 프롬프트에 전부 실어 방어(구현 = 각 레포
  `.claude/workflows/commit-review.js`, 반증검사 5케이스 통과 — 같은 라인 2관점→verify 1회 /
  다른 라인→2회 / 병합 기각 경로 / 지적 0건 / 관점 사망 시 미완결 유지).

## ⚠️ 2026-08-28 개정 — 초판 병합 키는 절감이 0 이었다

08-27 처방을 첫 A티어 회차에서 실측하니 **`mergedCount` 가 전부 1**(원시 8건 → verify 8개)이었다.
그런데 실제 중복은 2쌍이었다 — **관점마다 같은 결함을 다른 라인으로 인용**한다(`:1291` vs `:1010 부근`,
한쪽은 "8개" 다른 쪽은 "7건"으로 개수까지 다르게 셌다). 즉 위의 "44% 중복"은 **정확일치 키로는
회수되지 않는다**. 병합 로그가 찍힌다고 병합이 된 것이 아니다.

**개정 3가지**(엔진 = 전 레포 + 킷 사본 11곳 동일):

1. **병합 키 완화** — 같은 파일 안에서 ①라인 근접(±15, `mergeLineWindow`) ②제목 토큰 **overlap 계수**
   ≥0.3(`mergeTitleSim`) ③둘 다 라인 미상이면 원문 일치. 자카드가 아니라 overlap 인 이유 = 제목이
   3~5토큰으로 짧아 핵심 명사를 공유해도 자카드가 0.2 아래로 떨어진다(실측 케이스 = 자카드 0.17 / overlap 0.33).
   ⚠️**병합은 서로 다른 관점 사이에서만** 한다 — 같은 관점이 같은 파일에 2건을 냈다면 그 에이전트는 둘을
   다른 결함으로 본 것이다. 키를 푸는 만큼 이 축으로 과병합을 막는다.
2. **verify 를 파일 단위 배치로** — 지적 단위로 돌리면 같은 파일을 지적 수만큼 다시 읽는다(실측: 파일 2개를
   8번 = ≈685k). 파일당 1에이전트가 **독립 판정 블록**으로 처리하고 `verifyBatchMax`(기본 6)로 쪼갠다.
   ⚠️**대가 = 에이전트 1개 사망이 그 파일의 지적을 통째로 삼킨다**(지적 단위였을 땐 1건 손실). ⇒ 반환에서
   **입력으로 준 id 만** 취하고, 미판정이 남으면 그 건만 재시도하며, 그래도 없으면 `unverified` 로 남겨
   **`reviewComplete=false`**. 미판정을 기각으로 접으면 "거짓 기각 = 결함 유출"을 스스로 만드는 셈이다.
   ⚠️판정 오염(하나를 기각한 뒤 나머지도 기각하는 후광) 위험은 남는다 — 독립판정 지시 + id 별 reason
   필수로 완화했고, **다음 회차에서 CONFIRMED 수가 줄지 않는지로 검증**한다.
3. **병합 0건 경고** — 관점 ≥2 인데 `uniq === raw` 면 결과에 `mergeStats.warning` 을 싣는다. 08-28 에는
   로그만 찍혀 결과만 본 호출자가 병합이 동작한 줄 알았다.

**검증**(2026-08-28, 실제 파일에서 로직을 추출해 실행 — 사본 재작성 금지): 병합 6케이스(실측 2케이스 재현
포함) + 배치·미판정 회수 5케이스 전부 통과, **반증 3종**(제목병합 OFF → 미병합 / 라인병합 OFF → 미병합 /
위조 id 는 미판정으로 남음)이 실제로 red 를 냈다. 남은 실측 항목 = 다음 A티어 회차의 ①`mergedCount`>1 그룹
발생 ②verify 에이전트 수가 파일 수에 수렴 ③CONFIRMED 수 불감소.

부수 운용(프로젝트 규약 배치): 중간 라운드 테스트 `-pl` 영향 모듈만·전량은 마커 직전 1회 /
E2E 위임 서브셋 / 착수 전 사전조사 기본 1에이전트(대형 조사의 적대 검증 단계는 유지 — 19에이전트
조사에서 1차 서술의 61%가 ADJUSTED 였던 실측).
