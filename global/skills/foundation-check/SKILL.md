# foundation-check — 첫 화면 전 기반 점검

## 왜 있나
화면을 다 만든 뒤 찾은 결함의 상당수는 **모든 화면이 공유하는 기반의 결정이 비어 있던 것**이었다. 사후 수리는 대개 기반 한 곳으로 끝나지 않고 화면 호출부 수십 곳을 함께 고쳤다 — 이 점검의 가치는 "처음 정할 때 확산을 막는다"이다(입증 불가한 반사실이라 과신 금지). 근거·표본 = `~/.claude/rules-rationale/foundation-check.md`.

## 언제 돌리나
- 첫 화면 착수 전 / **인계받은 초기소스**·팀 공통 모듈(래퍼·예외 처리·보안 설정)이 들어온 직후 / 그것들이 pull 로 바뀐 직후.
- 인계 초기소스의 전역 필터·변환기도 대상이다 — 우리가 쓰지 않은 코드가 뿌리였던 사례가 있다(전역 JSON 이스케이프 → 화면 수십 곳 엔티티 수리).

## 절차
1. **스택 판별**(모든 pom 재귀): `org\.egovframe\.boot|spring-boot` 가 있으면 → `stacks/boot.md` / `egovframework\.rte\.version` 3.x + `<packaging>war` 면 → `stacks/egov-jsp.md`. 둘 다 아니면 질문만 쓰고 위치는 직접 찾는다.
2. 아래 **핵심 계열**마다 스택 문서의 확인 위치를 실물로 본다(추측 금지 — 근거 = 파일:라인/명령).
3. 결과를 표로 낸다: `계열 | 판정(통과/결함/해당없음/미확인) | 근거 | 기반 수리안`.
4. **결함은 첫 화면 전에 기반에서 고친다**(화면에서 우회 금지). 팀 소유 모듈이라 못 고치면 사용자에게 "팀 요청 목록"으로 보고하고, 화면 쪽 공통 규약(예: 호출부 가드 형태)을 정해 둔다.
5. 고칠 수 없는 항목은 대신 **기계 검사**(계약 테스트·lint·훅)를 둘 수 있는지 판단한다.

## 핵심 계열 — 질문 / 통과 기준 / 사후 수리 실례
### C1 요청 결말(화면 비동기)
- 질문: 공통 요청 경로가 **8결말**(200 · 400 · 403 · 409/503 · 500 · 비JSON 본문(오류 HTML·빈 본문) · 무응답 · 전송 전 예외)마다 화면에 무엇을 넘기나? 비멱등 요청이 무응답으로 끝나면 "실패"로 단정하나? 연타·늦은 응답은 누가 막나?
- 통과: 결말별 동작이 **한 곳**에 정의 · 실패 sentinel 계약(성공 콜백 선두 가드)이 명시 · 비멱등 무응답 = "결과를 확인하지 못했다" 안내 · 제출 = 드롭 가드 / 조회 = last-wins 수단이 공통에 있다 · 응답 본문을 다 읽기 전에 로딩 표시가 걷히지 않는다. 가능하면 8결말 계약 테스트(jsharness 류).
- 실례: 무응답 등록을 실패로 단정 → 재등록 중복 / 400 사유를 "(400)"으로 삼킴 / 전송 전 예외로 콜백 미호출 → 화면 잠금 영구화 / 로딩이 본문 읽기 전에 걷혀 재클릭.

### C2 오류 응답
- 질문: 예외가 응답에 내부 문구(JDK·라이브러리 메시지)·입력값·내부 ID 를 싣나? 404/500 에 프레임워크 기본 화면이 나오나? 잠금 실패·연결 고갈이 사유 없는 500 인가? 정상으로 끝나는 업무 예외가 ERROR 로그를 남기나?
- 통과: 응답 문구 생성이 공용 1곳(우리가 던진 업무 예외만 원문, 나머지 고정 문구) · 오류 화면 존재 · 잠금 실패 = 409, 연결 고갈 = 503 + "잠시 후 다시" · 업무 예외는 ERROR 아님.
- 실례: 컨트롤러마다 `fail(e.getMessage())` 로 내부 문구 노출 → 공용 헬퍼 신설 후 수십 곳 치환 / 거부 사유에 요청자 IP 반향 / Whitelabel 화면.

### C3 문자 처리
- 질문: 출력 이스케이프는 어디서 몇 번 하나(저장 전·직렬화·출력)? 입력 필터·JSON 직렬화가 HTML 엔티티를 만드나? 인코딩 필터가 체인 맨 앞인가? DB 연결 문자셋이 utf8mb4 인가?
- 통과: **출력 시점 1회** 이스케이프가 원칙이고, 저장·직렬화 단계 변환이 있으면 화면 디코드 정책이 한 곳에 있다 · 이모지·한글 왕복(저장→조회→수정 저장) 1회 확인.
- 실례: 전역 직렬화 이스케이프가 만든 `&lt;` 가 화면에 그대로 보이거나 수정 저장으로 DB 에 박힘 / 한글 이중 인코딩 / 연결 문자셋이 utf8mb3 로 되돌아가 이모지 저장 실패.

### C4 인증·인가·세션
- 질문: 인증 정본이 하나인가(세션 vs 토큰·쿠키 사본)? 미등록 URL 은 기본 거부인가(메뉴 숨김 ≠ 인가)? 다건 처리 루프에서 인증 실패가 건별 catch 에 삼켜지나? 배경 폴링이 유휴 만료를 연장하나? 세션 쿠키가 모듈(관리자/사용자)별로 분리되나? 서명키·시크릿이 프로파일별·미추적인가? 파일 다운로드가 직접 호출로 열리나?
- 통과: 정본 1개 · 인가 기본 거부 · 루프 전 fail-fast · 유휴 판정은 서버가 마지막 사용자 활동으로 · 시크릿 격리.
- 실례: 로그아웃 뒤 토큰 사본으로 로그인 부활 / 다건 삭제가 인증 NPE 를 "0건 삭제(N건 실패)"로 위장 / URL 직타로 숨긴 화면 진입.

### C5 트랜잭션·동시성
- 질문: 트랜잭션 AOP 포인트컷이 **자체 패키지**의 서비스 구현을 덮나(프레임워크 기본 패키지만 덮는 설정이 흔하다)? 채번은 어떻게(MAX+1 금지)? 같은 자원을 잡는 경로들의 잠금 순서 규약이 있나? 교착·잠금 대기 초과는 무엇으로 응답하나?
- 통과: 포인트컷 ⊇ 자체 패키지(아니면 `@Transactional` 규약 + 검사 수단) · 채번 = DB 시퀀스·AUTO_INCREMENT · 경합 자원은 **두 컨텍스트 동시 조작 E2E** 로 확인 · 교착 = 409.
- 실례: 포인트컷이 자체 패키지를 안 덮어 다중 쓰기 부분 저장 / 댓글·게시물 번호 충돌 / 신규 신청 동시 저장 교착.

### C6 저장값 정합
- 질문: 소프트 삭제된 행이 수정 저장으로 되살아나나? 화면이 보내지 않은 필드를 서버가 기본값으로 덮나? 빈 목록 저장(전체 해제)이 무시되나? 저장 실패 시 입력이 보존되나? 크기·길이·형식 상한이 서버·DB·화면 안내·`accept` 에서 같은 값인가?
- 통과: 수정 조건에 삭제 여부 · 신규 CRUD 마다 필드 소유권 표(화면이 정함/서버가 강제/저장값 유지) · 빈 목록 = 전체 해제 · 상한 정의 1곳에서 안내까지 파생.
- 실례: 삭제된 계정이 수정으로 부활 / 수정 저장이 기존 Y 를 N 으로 덮음 / 안내 문구의 업로드 상한이 실제와 다름.

### C7 파일 업로드·다운로드
- 질문: 공통 모듈이 저장 경로·소유권(남의 첨부를 내 글에 묶기)·확장자·크기·파일명(제어 문자)·다운로드 인가를 정하나?
- 통과: 공통 1곳 + 첨부 소유권 서버 판정 + 다운로드 인가.
- 실례: 다른 글에 달린 첨부를 내 글에 달아 열람 범위 확대 / 비인증 직접 다운로드.

## 부록 계열(증거 얇음 — 해당되면 한 줄 판정)
- 입력 허용목록 공통 계층: 페이징·정렬 파라미터 클램프, URL 스킴 가드.
- 접근성 공통 헬퍼: 같은 안내 재낭독, 대화상자 포커스 복귀·중첩 ESC, 그리드 키보드.
- 외부 연동(포털·SSO 등): 응답 계약 실측 픽스처, 장애 시 안내, 실패 사유 비노출.
- 복제본: 공통 JS·헬퍼가 모듈마다 복제돼 있으면 단일화 또는 짝 동기 검사.
- 운영: 로그 보관 상한, 커넥션 풀 상한, 로컬 기동 블로커, 빌드 저장소, 운영 DB 계정 권한, 캐시 키 누락 시 동작.
- SQL 관례: datetime 에 날짜 문자열 BETWEEN(종료일 누락 → `>= 시작 AND < 다음날`), 하드 DELETE 의 참조 정리, 운영 데이터의 테스트 시드.

## 하지 않는 것
- 도메인 로직·퍼블 정합 판정(화면형 — 첫 화면 전 판정으로 못 막는다).
- 판정 없이 "통과" 표기. 확인 못 한 계열은 `미확인` 으로 남긴다.
