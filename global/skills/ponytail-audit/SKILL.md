**이 스킬은 코드를 바꾸지 않는다.** 레포 안의 소스·설정·테스트 파일을 Edit·Write 하지 않고, 빌드·앱 기동·DB 쓰기도 하지 않는다 — 읽기·grep 만(리포트 파일은 레포 밖에만 쓴다, 4절). 사용자가 리포트를 보고 "2번, 5번 고쳐"라고 하면 그건 별도 구현 요청이다(그때는 그 작업의 규약을 따른다).

diff 하나를 다듬는 건 빌트인 `/simplify`, diff 의 결함 사냥은 `/code-review` 몫이다. 이 스킬은 **도메인 단위** — 이미 굳은 코드에서 결함과 군살을 찾는다.

## 0. 제안 시점과 운용 계약

**제안 시점** — 아래가 관측되면 "이 도메인(`<경로>`) 감사 돌릴까요?"를 한 줄 제안만 한다. 자동 실행하지 않고, 사용자가 승인하면 돌린다.
1. 한 도메인을 크게 손대는 작업에 착수할 때 — 그 도메인 대상.
2. pull·병합으로 팀 공통 모듈·인계 소스가 들어왔을 때 — 들어온 도메인 대상. 그 레포가 `foundation-check` 스킬의 적용 스택(그 스킬 description 의 스택)이면 그 스킬 제안과 함께 낸다(foundation-check = 화면이 공유할 기반 결정, 이 스킬 = 도메인 안의 결함·군살).
3. 배포·오픈 전 점검 얘기가 나올 때 — 이번 배포에서 바뀐 도메인부터.
4. 버그헌팅 회차를 마치고 다음 대상을 정할 때 — 군살(Lean) 축 보완.

**도메인 = 그 레포의 기능 단위 하나.** 관측으로 정한다:
- 멀티모듈 빌드(모듈마다 같은 기능 패키지 이름이 반복) → 기능 패키지 이름 하나 — 모듈마다 그 이름의 하위 트리와, 그 기능의 매퍼·템플릿·뷰 파일까지.
- 단일 모듈 → 컨트롤러·핸들러가 놓인 기능 패키지 하위 트리 하나(공통·유틸 패키지는 그 자체가 도메인).
- 스크립트·설정 레포 → 최상위 디렉터리 하나, 크면 그 아래 기능 폴더 하나(스킬 폴더 하나·훅 묶음 하나 등).
- 사용자가 도메인을 지정하지 않았으면 후보 표(경로·`wc -l` 줄 수)를 내고 고르게 한다. 레포 전체를 원하면 도메인마다 따로 돌린다.
- 지도 그리기(1절)에서 깊게 못 읽을 부분이 생기면 그 부분을 `Not checked:` 에 적고, 다음 회차를 위한 더 작은 도메인 분할을 제안한다.

**운용 계약:**
- **실행자 = 읽기 전용**(팀 좌석·서브에이전트 등 레포를 바꾸지 않는 실행자). 리포트 형식·근거 표는 4절.
- **반증 = 리포트 작성자가 아닌 쪽**(보통 실행을 맡긴 세션)이 지적마다 한다 — 3절.
- **분류:** 그 레포에 결함 장부(이월 버그·결함 목록 등 — 레포 문서·프로젝트 memory 에서 찾는다)가 있으면 지적마다 대조해 `기지(장부 항목)`·`신규` 를 표시하고, 신규는 반증 뒤 장부에 등재한다. 장부가 없으면 리포트 파일이 장부 역할을 한다.
- **후속:** Must fix → `diagnose-bug` 스킬 흐름 / 군살(Lean) → 작은 묶음 커밋 + 그 레포의 리뷰 티어 규약(실행 의미가 바뀌면 A티어). 리포트의 수정안을 자동 적용하지 않는다 — 고치는 건 별도 구현 요청이다.

## 1. 먼저 지도 그리기

새로 인계받은 레포를 맡은 시니어 개발자처럼, 장애가 나면 내가 호출된다는 마음으로 감사한다. 중요도 순서: 정확 → 안전 → 부하 견딤 → 테스트 → 속도 → 군살(lean). 군살도 중요하다 — 남는 줄은 모두 나중에 읽고 시험하고 고쳐야 한다. 사용자가 청한 리포트이니 빠짐없이 낸다.

- 0절의 도메인 하나를 감사한다. 도메인 밖은 도메인이 호출하거나 도메인을 호출하는 경로만 읽는다.
- README, 배포·빌드 설정, 의존성 목록, 도메인의 진입점(main·라우트·핸들러·배치·CLI 명령), 도메인의 테스트를 읽는다.
- 예상 부하를 정한다: 혼자 돌리는 스크립트인가, 여러 사용자·프로세스가 동시에 쓰는가. 규모 판단은 그 부하 기준이며, 가정한 부하를 리포트에 적는다.
- 주요 흐름을 끝까지 따라간다: 데이터가 어디로 들어와, 무엇이 저장되고, 무엇이 나가는가. 사용자 입력·돈·인증·데이터 쓰기·배치·프로세스 간 공유 자원 경로는 끝까지 읽는다.
- 큰 도메인: 파일 순서가 아니라 실수 비용이 큰 곳부터 깊게. 읽지 않은 부분은 적는다.

## 2. 찾을 것

1. **결함(Bug):** 틀린 결과, 크래시, 놓친 경계(빈 값·0·마지막 항목·반올림·시간대), 함수 반환과 어긋나게 쓰는 호출처, 같은 규칙을 두 곳에서 다르게 적용.
2. **위험(Risk):** 보안 구멍(인젝션·약한 난수·코드 속 비밀값·사용자 입력 검증 누락), 데이터 손실(삼킨 오류·잘못된 쓰기 순서·트랜잭션 없음).
3. **규모(Scale):** 한 명일 땐 맞고 여럿이면 틀린 것 — 확인 후 쓰기 경합, 모든 프로세스가 같은 일을 반복, 계속 자라기만 하는 메모리·목록, 항목마다 쿼리 1개, 큰 입력의 O(n²), 공유돼야 할 프로세스별 상태.
4. **테스트 공백:** 위험한 로직(분기·파서·돈·보안·데이터 쓰기)인데 깨지면 실패하는 테스트가 없음. 커버리지가 아니라 좋은 테스트 하나.
5. **속도:** 큰 지연은 문제. 작은 개선(핫 루프 안 반복 작업)은 제안 — 밀리초가 중요한 소프트웨어도 있다.
6. **군살(Lean):** 없어야 하거나 더 작아야 할 코드.
   - delete: 죽은 코드, 안 쓰는 옵션·플래그·설정, 추측성 기능
   - reuse: 같은 일을 하는 헬퍼 두 개(하나만 남기고 경로를 적는다)
   - stdlib / native: 표준 라이브러리·플랫폼이 이미 하는 일, 몇 줄이나 플랫폼으로 되는 일을 하는 의존성
   - yagni: 구현 1개짜리 인터페이스, 제품 1개짜리 팩토리, 호출만 넘기는 래퍼
   - merge: 함께 바뀌어야 하는 거의-복사본
   - split: 서로 무관한 일 여러 개를 하는 함수·클래스. 줄 수가 아니라 일 단위로 쪼개고, 함수를 짧게 만들려고만 존재하는 헬퍼로 쪼개지 않는다.

**하한선 5항목은 군살이 아니다** — 트러스트 경계 입력검증·데이터 손실 방지 에러처리·보안·접근성·명시 요청 기능을 "지울 것"으로 지적하지 않는다.

## 3. 보고 전 확인

- 지적마다 구체 사례가 있어야 한다: "이 입력·상황이면 이런 틀린 결과". 사례가 없으면 지적도 없다.
- **지적마다 근거 `file:line` 과 그 줄의 원문을 그대로 인용한다**(코드·주석·문구 모두 — 요약·의역 금지). 인용은 실제 파일에서 옮기고, 원문에 없는 성격 규정("사문", "아무도 안 씀" 등)은 인용 밖의 내 판단으로 구분해 쓴다. 호출 경로·런타임 동작처럼 직접 확인하지 못한 부분이 지적의 근거면 그 지적에 `미검증` 라벨을 붙인다.
- **지적의 반증은 리포트 작성자가 아닌 쪽이 지적마다 한다**(보통 실행을 맡긴 세션 — 인용을 원문과 대조하고 사례를 다시 확인). 작성자의 자기 확인은 반증이 아니다. 리포트는 반증 전 상태임을 머리에 적고, 고치기 전에 반증을 받으라고 사용자에게 알린다.
- 인용에 비밀값(비밀번호·토큰·키·개인정보)이 걸리면 `<REDACTED>` 로 가린다.
- "안 쓰인다"는 grep 한 번으로 확정하지 않는다 — 도메인 밖까지 트리 전체를 grep 한다(테스트·픽스처·설정·문자열·동적 참조 — XML·템플릿·JS 문자열 포함). **히트 수는 `grep -c`·`grep … | wc -l` 로 센다** — `head` 등 출력 캡으로 본 목록은 개수 근거가 아니다. grep 0건은 부재 증명이 아니다: 검색 모집단과, 실제로 쓰이는 이름 하나로 같은 grep 이 히트하는지(양성 대조)를 함께 본다.
- 한계를 적은 `ponytail:`(또는 업스트림 `shortcut:`) 마커가 달린 지름길은 결정이지 지적이 아니다 — 단 예상 부하가 이미 그 한계를 넘었거나, 마커가 약속한 동작이 실재하지 않으면 지적한다.
- 통하는 가장 작은 수정을 제안한다. 코드를 지우는 수정을 우선한다. 문제가 요구하지 않는 계층·프레임워크·설정을 더하지 않는다.
- 취향 지적·"고려해 보라"·막연한 걱정 금지.

## 4. 출력

쉬운 한국어로: 짧은 문장, 일상어. 전문용어는 처음 쓸 때 풀이한다. 독자는 이 코드를 처음 볼 수 있다.

**범위가 크면(지적이 많거나 리포트가 길면) 전문은 레포 밖 파일**(예: `/tmp/ponytail-audit-<레포>-<YYYYMMDD>.md` — 레포 안에 쓰지 않는다)에 쓰고, 회신에는 그 경로와 요약(판정·묶음별 건수·지적 제목)만 낸다 — 긴 회신은 잘린다.

머리에 `반증 전 리포트`, 그다음 `감사 범위:`(도메인 경로·줄 수)와 `이 도메인이 하는 일:` 두세 문장, 가정한 부하로 시작한다.

그다음 지적을 세 묶음으로, 중요한 것부터(빈 묶음은 생략):
- **Must fix:** 결함·보안·데이터 손실·예상 부하에서 깨짐.
- **Should fix:** 테스트 없는 위험 코드·실제 느림·중복·일이 섞인 함수·없어야 할 코드.
- **Nice to have:** 작은 속도 개선·더 짧은 형태.

번호는 묶음을 넘어 이어 매긴다("2번, 5번 고쳐"라고 말할 수 있게). 최대 20건 — 작은 것을 뺐으면 몇 건 뺐는지 적는다. 지적마다 다섯 부분, 각각 한두 문장:

```
2. **마감 배치가 날짜를 하루 앞당긴다** (`batch/CloseDay.java:40-52`)
   - 근거: `:44` `LocalDate today = LocalDate.now(ZoneOffset.UTC);`
   - 이건 뭔가: 자정에 그날 주문을 마감·정산하는 배치.
   - 문제: 날짜를 UTC 로 잡아, 한국시간 00:30 주문이 전날로 정산된다.
   - 수정: 날짜를 서비스 시간대로 한 번 계산 — `LocalDate.now(ZoneId.of("Asia/Seoul"))`. 한 줄, 다른 변경 없음.
   - 안 고치면: 새벽 주문 날짜가 틀려 정산 담당이 손으로 고친다.
```

끝에:
- `판정:` 한 줄 — 건강함, 또는 먼저 고칠 것.
- `Lean: -<N>줄, -<M>개 의존성 가능.` (군살 지적이 있을 때)
- `미검증:` 라벨을 붙인 지적 번호(없으면 생략).
- `Not checked:` 읽지 않았거나 실행해 볼 수 없었던 부분.
- **근거 표(필수, 지적이 있으면 생략 불가)** — 지적마다 한 행:

  | # | 파일:라인 | 실제로 친 확인 명령(1줄) |
  |---|---|---|
  | 2 | `batch/CloseDay.java:44` | `grep -rn -F 'ZoneOffset.UTC' src/main/java \| wc -l` |

  명령 칸은 이번 감사에서 실제로 실행한 명령만 적는다(안 친 명령을 적지 않는다). 칠 수 없었으면 `미실행` 이라 쓰고 그 지적을 `미검증` 으로 둔다.

지적이 없으면: `감사 범위:`·`이 도메인이 하는 일:` → `건강함. 고칠 것 없음.` → 무엇을 확인했는지 한 줄.

1회 리포트, 코드는 바꾸지 않는다.
